# Assumptions

One line per decision that the specification left open (what, why).

- P0: `pytest`, `ruff` and `pip-audit` are listed in `requirements.txt` (the spec allows one requirements file), so the Docker image built from the lock file also contains them. Simplicity over image size.
- P0: `effective_llm_mode` is also `offline` when `LLM_MODEL` is empty, because LiteLLM cannot be called without a model string.
- P0: `.env.example` uses the placeholder `provider/model-name` for `LLM_MODEL` (decision D13: no hard-coded model names).
- P1: Demo IDs (customer, product, store, branch, sale, transaction) are integers and dates are ISO `YYYY-MM-DD`, to keep the CSV files small (total about 17 MB).
- P1: Pattern R1 says total revenue falls about 8%, but the `trend` detector in P6 only flags changes of at least 10%. Store 03 is therefore a large store (27% of sales), so its September drop moves the total by more than 10%. The planted 2026-08-12 spike also inflates August, which makes the August-to-September change larger still. Bank pattern B1 uses the same approach (Branch 07 holds 27% of transactions).
- P2: Every cell is read as text first (CSV and XLSX alike), so cleaning code is identical for both. Excel files are read with cached values only; a formula without a cached value becomes an empty cell.
- P2: A single-sheet workbook uses the file name as table name; a multi-sheet workbook uses the sheet names. Tables may not be called `base` or `data` (the flat views); such names get a numeric suffix.
- P2: Number strings with 13 or more digits, leading zeros (`007`) or a leading `+` with 7+ digits stay text, because they are identifiers, phone numbers or card numbers. "1,234" is read as 1234 (US style); "12,5" as 12.5.
- P2: For PII, the word `name` alone only counts for people (`name`, `customer_name`, `full_name`...), so `product_name`, `store_name` and `branch_name` stay. Value rules (email, phone, card) run on text columns only; plain digit strings are not treated as phone numbers because amounts look the same.
- P2: `null_pct` is on a 0..100 scale. Date columns are stored as DuckDB `DATE`; the time of day is dropped (reported as a cleaning action).
- P2: Relationship proposals additionally require that the fact column reaches at least 20% of the dimension keys (`coverage`) and pick at most one join per dimension table. Without this, small integer columns such as `quantity` would be proposed as keys for `stores`.
- P3: The retail `revenue` fallback to "generic `total_amount`" is written as a `fallback_expr` on the metric itself (same id `revenue`), so the primary metric id stays stable. A requirement written as `column:fee` means a literal column name instead of a role.
- P3: `requires_values` are checked against the category list of the mapped column (columns with more than 30 distinct values have no category list, so such a metric is reported unavailable). `failed_rate_pct` additionally requires the value `failed`, because a rate of 0 on data without failures would be misleading.
- P1: The YoY patterns (R7, B7) are measured on July-September 2026 vs July-September 2025. The generator produces roughly +44% for Home & Garden (overall +4%) and +65% for mobile (overall +10%).
- P4: SQL is validated by parsing (sqlglot, DuckDB dialect) and then `EXPLAIN` against the real schema; the normalized text (comments removed) is what runs. The only table is `data`; its own CTEs are allowed. `generate_series`/`range`/`unnest` are the only table functions allowed. Statements longer than 5000 characters are rejected.
- P4: A query is stopped after `QUERY_TIMEOUT_S` by interrupting a worker thread's cursor. Results are cut at `RESULT_ROW_LIMIT` rows with a note.
- P4: Result hashes compare rows only (not column names), sorted, with numbers rounded to 4 decimals. Candidates that fail after two repairs still count in the total when voting, so a 1-of-3 result is shown as unverified.
- P4: The Egress Gate scans for e-mail addresses, Luhn-valid card numbers (13-19 digits) and phone numbers (international `+` numbers, `(415) 555-2671`, `415-555-2671`). Payloads over 200,000 bytes are blocked. The size check runs before the scan, and the e-mail pattern is linear-time (a test caught a first version that needed 130 s for a 200 KB payload).
- P4: In `demo` and `cloud` mode the provider counts as external (bytes are counted). `local` mode blocks any endpoint that is not loopback/private.
- P4: Offline mode matches the question text against the golden questions after lower-casing and removing punctuation. It works only for the demo datasets (`retail`, `bank`); an uploaded dataset in offline mode always gets the offline message.
- P4: The prompt sends column names, types, roles, null %, min/max and metric expressions. Category values are sent in `demo` and `local` mode, and in `cloud` mode only when `SEND_CATEGORY_VALUES=true` (D7). Query result rows are never sent to the model (D8).
- P5: With the default (full) date range there is no earlier period in the data, so KPI deltas show "n/a" until the user narrows the date range. A previous period with no rows at all also shows "n/a" (not 0).
- P5: A numeric slicer keeps only rows whose value lies in the range, so rows with an empty amount are dropped once the slider is moved; the slider has no effect until it is moved. Category slicers with nothing selected mean "all".
- P5: Dashboard queries are built by code (not by the model) and are run directly with the time limit; they read `data` and, for the previous period, `base`. Only model-written SQL goes through the SQL validator.
- P5: Streamlit 1.64 stretches charts and tables by default, so the deprecated `use_container_width` argument is not used.
- P5: `scripts/perf_check.py` on 1,000,000 fact rows: all dashboard queries plus the slicer rebuild take about 0.9 s in total on this machine. Loading and cleaning 1,000,000 text rows is much slower (about 70 s); this goes into `KNOWN_LIMITATIONS.md`.
- P6: Spec R1/B1 says total revenue falls "about 8%", which can never pass the 10% trend rule. The demo data therefore plants large stores and branches (about 27% share each), so the total falls 20-26% and both the trend and the driver detectors fire. The planted pattern (one store or branch collapses in 2026-09) is unchanged.
- P6: Trend uses monthly totals without adjusting for the number of days in a month. February to March (+10.7% from length alone) could be flagged on real data; this is listed in `KNOWN_LIMITATIONS.md`.
- P6: Other additive metrics get a trend card only when their change differs from the primary metric's change by at least 10 points, otherwise every metric would repeat the same story. Percent metrics and the primary metric are always checked.
- P6: The driver detector also requires that the top category's share of the change is at least 1.5 times its share of the previous level; without it a binary dimension such as channel would "explain" every change.
- P6: Anomalies use the weekday-median residual with the spec's robust z. A third, weaker day (2026-08-04 in retail) is also flagged; it is not a planted pattern, so it counts as a false positive of this detector and is listed in KNOWN_LIMITATIONS.md (max 3 anomalies).
- P6: Churn uses the last complete month against the mean of the 6 months before it, needs `customer_id` and `date`, and requires at least 3 months. Flag at 10 percentage points or more.
- P6: Findings carry neutral aliases (`f1`, `f2`, ...) when sent to a model, because real ids contain category values. Cards are mapped back to real ids in code; code also overrides priority and confidence and clears `expected_impact` so a model cannot invent them.
- P6: In `cloud` mode findings with fewer than K_ANON_MIN rows are not sent; they still get a template-written card, and the section shows a note. Category values become "Segment A/B/..." unless SEND_CATEGORY_VALUES is true, and are restored in the returned text.
- P6: Grounding allows only numbers that are in the finding's facts (rounded to the displayed precision, or within 0.5%). The code adds no other derived values, so templates and the model must not compute new ones. Number words such as "twelve percent" are not parsed (documented, not required by the spec).
- P6: Detector timing on 1,000,000 fact rows (`scripts/perf_check.py`): about 3 s on all rows and under 1 s on a six-month slice.
- P7: Streamlit runs the code of every tab on each interaction, so the slow parts are button-driven: "Find insights" runs the detectors (and the AI wording) once per dataset build, filter state and metric set and keeps the result; the Ask tab only works when a question is submitted.
- P7: Demo datasets are loaded and built with the default choices as soon as they are selected. An upload is read when the files change; nothing is built until "Confirm and build" is pressed, and the page then reruns so the slicers and all tabs see the new dataset.
- P7: The role selectors and join checkboxes preview the flat view in a separate DuckDB view named `preview` (a reserved table name), so a half-edited selection never changes `base` or `data` under the dashboard.
- P7: A role mapping is checked for column existence and type (numbers for amount, cost and quantity; a date for date) before a build; unknown roles are rejected.
- P7: Cached dashboard queries are keyed by dataset id, dataset version, filter hash and metric definitions. The id keeps sessions apart even when two uploads have the same version hash.
- P7: "Clear session" closes the DuckDB connection, empties the audit log and clears Streamlit's data cache (that cache is shared by all sessions, so other visitors recompute once). The password login is kept. Inactivity cleanup is only what Streamlit does when a session ends (best effort, documented in KNOWN_LIMITATIONS.md).
- P7: For a clarifying question the buttons offer the available metrics; a click asks the original question again with "Use the metric X." appended. Uploaded datasets get generic suggested questions built from their metrics and columns; demo datasets use the golden set.
- P7: Unknown exceptions are logged with a reference id, the exception type and the stack frames only. The exception message is left out because a database error can quote a data value.
- P7: The AppTest smoke tests set LLM_MODE=offline and empty key and password through environment variables, which take precedence over any local `.env` file.
- P8: Two result sets are equal when they have the same rows in any order and numbers agree after rounding to 2 decimals. A golden question passes only on an equal result set; an answer that needs a clarification or is refused counts as a failure.
- P8: The evaluation report separates "verified" answers (the model's own check passed) from "unverified" ones, so the accuracy of each group can be read on its own. Only numbers found in a stored report under `reports/` are quoted in the documents.
- P8: A run where most calls fail for a provider reason (quota, unknown model) is not an accuracy measurement. It is kept as a report but described as inconclusive.
- P8: Offline mode answers only the 40 golden questions; `scripts/eval_golden.py --model offline` must give 40/40 and exits with 1 otherwise.
- P8: `scripts/check_payloads.py` reads an exported audit log (JSON lines) and exits with 0 (clean), 1 (a payload matches an email, card or phone pattern) or 2 (the file is not a valid audit export).
- P8: The chaos tests replace `LiveProvider._call_litellm`; they check timeouts, rate limits, malformed and empty replies and show that the user always gets a friendly message and a fallback.
- P8: Load and clean speed: text cleaning and parsing run once per distinct value of a column and the result is spread back to the rows (`Distinct` in `core/ingest/cleaner.py`). Results are identical to the per-cell version (all cleaning tests pass, plus a test with many repeated values). Load, clean and profile of 1,000,000 rows went from about 36 s to about 6 s on the repeated demo data; a table whose text columns are nearly all unique (ids, free text) gains much less.
- P8: Date format choice (month/day or day/month) now counts distinct values instead of rows; the ambiguity warning is raised under the same conditions for normal data.
- P8: The model named in the local `.env` (`gemini/gemini-1.5-flash`) is retired by the provider and every call was rejected; that run was deleted. The evaluation was run once with `gemini/gemini-flash-latest`, which the same key accepts. The key hit the provider's rate limit after 4 questions, so the stored report is inconclusive (see KNOWN_LIMITATIONS.md).

## Finalyzer v3
- U0: The v2 Streamlit app and tests stay in place (root .venv); the v3 backend lives in ackend/ with its own venv. Both have a package called pp, so the two suites run in separate processes (see docs/ARCHITECTURE.md).
- U0: load_dotenv(override=True) was removed from core/config.py and pp/main.py. It let a local .env override real environment variables and broke the smoke tests; settings still read .env through pydantic.
- U1: Frontend uses React 18 (not 19) because the pinned component libraries are tested with 18; Tailwind v4 through @tailwindcss/vite; lint with oxlint now, ESLint security rules are added with the frontend wiring.
- U1: Sign-in attempts are counted per address even when the caller has a valid cookie, so one's own account gives no extra attempts against others. Failure counters are forgotten after 60 quiet minutes, otherwise rare typos would add up to a lock.
- U1: The password check also rejects a listed password with digits or symbols appended; the embedded top-10,000 list has only 10 entries of 12+ characters, so a plain lookup would let password1234 pass.
- U1: The OpenAPI document is available in test and development and switched off in production; Swagger UI is not served because it loads scripts from a CDN, which the CSP forbids.
- U1: The last_admin guard is unreachable through the API (sessions end when an admin is deactivated), so it is tested at service level as defence in depth.
- U4: Uzbek letters follow section 5.2 even where the spec table shows ASCII: `soʻm` (U+02BB) in currency text, `oʻ` and `gʻ` everywhere; the tutuq belgisi stays an ASCII `'` (`ma'lumot`, `mas'ul`).
- U4: Spacing: digit groups use U+202F; a number is joined to its unit word (`12,8 mln`, `12,8 mln soʻm`) with U+00A0 so a line never breaks inside; English units are glued (`12.8M`) and `UZS` is followed by U+00A0. Negative numbers use a plain hyphen-minus (it pastes into spreadsheets and parses back); a missing value is an en dash.
- U4: Rounding is half up on the shortest decimal text (1.005 gives 1.01), not half even; the frontend must do the same (`toFixed` is wrong for 1.005). English short dates are ISO (`2026-08-12`) because `12/08/2026` is ambiguous.
- U4: Frame keys are `type.direction.level` with direction `up`, `down` or `neutral` (spec `driver_negative` is `driver.down`) and level `simple`, `expert` or `simpler`. 18 finding types give 26 type/direction pairs and 78 frames per language. The `concentration` frame uses the ready genitive `{metric_gen}`. The spec example `«{segment}» da` is rewritten to `... tekshiring: «{segment}».` because rule 1 forbids suffixes on values.
- U4: Direction words are checked with patterns (`oshdi`, `oshadi`, `oshib` ... ), not only the four listed forms, because frames also use present and continuous tenses. The patterns live in `core/i18n/polarity.py` and will also serve the grounding check in U6.
- U4: The glossary has 189 entries per language (spec: at least 150). Glossary tokens in text are written `[[key|visible text]]`; the jargon lint ignores what is inside them. Everything the agent wrote is `reviewed: false` and listed in `docs/uz_review.md` (regenerate with `python scripts/gen_uz_review.py`; a test fails if the file is stale).
- U4: `match_key` removes apostrophes completely, so `mas'ul` and `masul` are the same word; Russian and Uzbek Cyrillic are transliterated with one table used on both sides of every comparison (`ж` becomes `j`, `х` becomes `x`).
